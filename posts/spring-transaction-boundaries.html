Spring 事务边界：回滚、传播与代理自调用 ​

创建一个项目时，可能既要插入项目记录，又要把创建者加入成员表。如果第二步失败，第一步也应撤销。@Transactional 可以表达这个要求，但判断它是否生效，不能只看方法上有没有注解，还要看调用有没有经过代理、哪些操作加入了事务，以及异常如何离开方法。

本文讨论常见的 Spring 命令式事务、代理模式和单数据源场景。代码均为说明边界的示意片段，省略依赖注入、实体及 Mapper 定义。

代理包住的，才是声明式事务边界 ​

可以先把调用理解为三层：

text
Controller 调用 Spring 管理的 Service
    → 事务代理按配置开启或加入事务
    → Service 执行业务和数据库操作
    → 代理根据返回结果与回滚规则提交或回滚
java
@Transactional
public void createProject(CreateCommand command) {
    projectMapper.insert(buildProject(command));
    memberMapper.insert(buildOwnerMember(command));
}

这段设计要成立，两个 Mapper 必须使用参与该事务的数据访问资源。给一个方法加注解，不会自动把另一个数据源、Kafka 消息或远程 HTTP 调用变成同一笔可回滚操作。事务范围应围绕需要共同成功的数据库修改设计。

异常类型和传播路径决定回滚结果 ​

在未修改默认回滚规则时，RuntimeException 和 Error 会触发回滚，受检异常默认不会。确实需要让某类受检异常导致回滚时，可以显式声明：

java
@Transactional(rollbackFor = ImportException.class)
public void importRecords() throws ImportException {
    // 写入数据库；校验失败时向外抛出 ImportException
}

另一个容易混淆的地方是 catch。如果方法把异常吞掉，正常返回，且事务此前没有被标记为仅回滚，代理通常会按成功路径提交。记录一条错误日志并不等于要求事务回滚。

但“捕获异常就一定能提交”同样不成立。假设内部方法通过代理加入同一事务，并已把共享事务标记为 rollback-only，外层即使捕获异常，提交时仍可能得到 UnexpectedRollbackException。应结合事务是否已经被标记回滚判断，不能只看最后有没有异常向外抛。

业务层可以把异常交给统一异常处理器生成响应；事务代理通常先处理事务结果，再由上层将异常转换成 HTTP 响应。返回一个表示失败的普通对象，则不必然触发回滚。

传播行为描述的是如何使用已有事务 ​

传播行为和隔离级别回答不同问题：前者关心调用链如何组织事务，后者关心并发事务之间的数据可见性与隔离。

传播行为当前存在事务时当前不存在事务时
REQUIRED，默认加入已有事务新建事务
REQUIRES_NEW挂起外层，开启独立事务新建事务
MANDATORY加入已有事务抛出异常
NOT_SUPPORTED挂起外层，以非事务方式执行以非事务方式执行

例如，写入“待发送事件”的方法如果必须和主业务共同提交，可以通过 MANDATORY 明确约束调用方。它表达的是“必须已有事务”，而不是悄悄替调用方新开一笔。

独立的审计记录可能适合 REQUIRES_NEW：内部事务一旦提交，外层随后回滚不会撤销它。但它不保证异常不会影响外层；内部异常若继续向外传播，仍可能触发外层的回滚规则。使用这种传播方式还需考虑额外连接需求，不能把它当成不付成本的隔离开关。

尤其不要为了“解耦”就提前提交一条成功通知：主业务之后可能回滚，通知却已经存在。是否独立提交，首先是业务语义问题。

同一个对象中的自调用不会开启新的代理边界 ​

在默认代理模式下，下面的调用没有重新经过 Spring 代理：

java
public void register() {
    this.saveAccount();
}

@Transactional
public void saveAccount() {
    accountMapper.insert(buildAccount());
}

如果外部调用的是未声明事务的 register()，不能指望内部 saveAccount() 上的注解单独建立事务。若外层本身已有事务，内部操作仍可能参与已有事务；问题是内部注解要求的新边界没有被应用，例如 REQUIRES_NEW 不会仅凭这次自调用生效。

一种清晰的做法是把需要独立事务语义的方法放入另一个 Spring Bean，由调用方通过注入后的对象调用。也可以在适合的场景使用 TransactionTemplate 显式组织边界。不要通过手动 new Service 来绕开容器，再期待声明式事务继续工作。

把事务边界与业务成功条件对齐 ​

设计入口时，可以先用一句话写清楚“这次成功必须同时留下哪些数据”。例如项目和创建者成员记录需要共同存在，就由一个 Service 方法组织它们；展示页的多个互不相关查询，则不必因为位于同一个接口里就强行建立很长的写事务。

事务中的远程调用和大量文件处理也会延长连接、锁等资源的占用时间。若把后续通知移出主事务，就需要同时说明失败后如何恢复，不能只移动一行调用便认为一致性问题已经解决。

排查时沿实际调用链确认三个事实：事务入口是否经过代理，数据库操作是否加入预期事务，以及失败时应用了什么回滚规则。它们比反复补注解更能解释提交结果。
