Spring Security 会话登录：身份如何跨请求保存 ​

用户名和密码验证通过之后，为什么下一次请求不需要再验证一遍？理解这个问题，需要把“验证本次凭据”和“保存后续可用的登录状态”分开看。前者产生认证结果，后者把认证结果与之后的请求关联起来。

本文以 Servlet 应用中的会话登录为例，关注 Spring Security 6 及之后常见的显式保存机制。JWT 等无状态认证使用不同的持久化策略，不能直接套用下面的 Session 流程。

安全过滤器在 Controller 之前工作 ​

一个经过 Spring Security 的典型请求可以概括为：

text
HTTP 请求
  → Servlet 过滤器链中的 DelegatingFilterProxy
  → FilterChainProxy
  → 选择匹配的 SecurityFilterChain，执行其中的过滤器
  → DispatcherServlet
  → Spring MVC 拦截器与 Controller
  → Service → Mapper

SecurityFilterChain 描述请求匹配条件以及要应用的安全过滤器。存在多条链时，由 FilterChainProxy 选择第一条匹配的链，不是把所有链中的规则全部叠加。所选链可以恢复身份、进行认证、校验 CSRF、防止未授权访问，也可能直接返回响应，不再进入 Controller。

Filter 属于 Servlet 请求处理机制，作用范围不限于 MVC Controller；MVC 的 HandlerInterceptor 则围绕已选择的处理器工作。它们与普通 Bean 的区别主要在参与请求处理的接入位置，不能简单理解为“普通 Bean 只在启动时有用，Filter 才会自动运行”。

登录同时解决凭据验证与状态建立 ​

用户名密码认证的一条常见路径是：

text
接收登录凭据
  → 创建未认证的 Authentication
  → AuthenticationManager 委派给适合的 AuthenticationProvider
  → 查询用户并校验密码
  → 得到已认证的 Authentication
  → 应用会话认证策略
  → 创建、设置并保存 SecurityContext

AuthenticationManager 是认证入口，用户名密码场景通常由相应 Provider 配合 UserDetailsService 和 PasswordEncoder 完成。认证成功后得到的 Authentication 包含当前主体及权限信息；它不是让业务代码自己拼一个“已登录”标记来代替密码校验。

SecurityContext 包含认证对象，SecurityContextHolder 提供当前执行上下文中的访问入口。常见 Servlet 配置使用线程关联的存储方式，因此设置 Holder 主要影响当前请求的处理，并不天然意味着下一个请求也能恢复这个身份。

自定义登录需要显式保存上下文 ​

Spring Security 提供的标准认证流程会完成其配置要求的相关步骤。若自己在 Controller 或 Filter 中调用认证管理器，就需要明确负责会话策略与上下文持久化。

下面是顺序示意，省略异常响应、依赖声明和应用配置，不能作为完整登录接口直接复制运行：

java
Authentication result = authenticationManager.authenticate(
    UsernamePasswordAuthenticationToken.unauthenticated(
        command.username(), command.password())
);

sessionStrategy.onAuthentication(result, request, response);

SecurityContext context = SecurityContextHolder.createEmptyContext();
context.setAuthentication(result);
SecurityContextHolder.setContext(context);
contextRepository.saveContext(context, request, response);

这里的 contextRepository 必须与安全过滤器使用的持久化配置一致；会话场景通常包含基于 HTTP Session 的仓库。只调用 SecurityContextHolder.setContext()，在采用 SecurityContextHolderFilter 的显式保存配置下，不能保证身份跨请求保留。

会话策略还可能包含会话固定攻击防护、并发会话控制和认证后的 CSRF 令牌处理。自定义认证入口应复用应用实际配置的策略，避免随意调用一个空策略就以为这些能力已经具备。具体组件组合需要根据所用版本和配置核对。

下一次请求怎样找到同一个身份 ​

浏览器通常携带名为 JSESSIONID 的会话 Cookie，名称也可以自定义。Cookie 主要携带会话标识，认证上下文保存在服务端会话存储中，并非每次都把用户名密码重新发送给应用。

text
浏览器携带会话 Cookie
  → 服务端找到对应 Session
  → SecurityContextRepository 读取安全上下文
  → 安全过滤器使当前请求可取得 Authentication
  → 授权检查通过后进入 Controller

因此 Controller 可以通过 Spring Security 提供的访问方式取得当前主体，也常见直接声明 Authentication 参数。业务层继续使用认证对象中的身份定位用户，不必让客户端再传一个可任意修改的用户 ID 来代表“我是谁”。

会话可能过期、被注销，或者当前请求只有匿名认证信息。不能仅凭“存在 Authentication 对象”就判断用户已经登录；应把访问限制交给相应的授权规则，并处理应用定义的未认证响应。请求结束后，安全过滤器还负责清理线程上的上下文，防止身份残留到复用的线程中。

身份恢复也不等于业务授权已经完成。例如某个接口允许登录用户访问，仍不意味着任意用户都能批准同一个项目的申请。服务端应结合当前认证身份与项目归属判断操作权限；客户端传入的项目编号只负责定位目标，不能成为权限证明。这能把安全链的通用访问规则与业务层的数据范围判断连接起来。

有 Session 也仍然需要关注请求来源 ​

浏览器会自动附带会话 Cookie，正是这种便利使会话认证需要考虑 CSRF。把接口改成接收 JSON，或把它标为 permitAll()，都不等于其他安全过滤器自动失效。是否要求 CSRF 令牌取决于请求和应用配置；不应仅为了让一个登录请求通过，就直接关闭整站防护。

调试“登录成功但下一次又未登录”时，可以顺着浏览器是否保存并发送 Cookie、服务端是否保存上下文、后续请求命中哪条安全链这条路径排查。跨域场景还要结合客户端凭据选项及 Cookie 属性判断，不能只检查认证接口有没有返回成功。
