Kafka 与 Outbox：把业务提交和通知投递衔接起来 ​

批准一条申请后，系统需要修改申请状态、增加成员，并通知申请人。直接在一个数据库事务里完成这些写入，适合许多简单场景；引入 Kafka 后，通知处理可以独立进行，但同时出现了一个问题：数据库提交和消息发送如何衔接？

下面从学习笔记中的通知场景抽象出一条通用链路。代码和表结构均为示意，省略序列化、依赖配置与完整错误处理，不代表一套可以直接运行的消息系统。

一笔数据库事务包不住两个系统 ​

先提交业务数据库，再发送消息，进程可能在两步之间停止，留下“申请通过但没有通知消息”的结果。若先发送消息，再提交数据库，又可能在数据库回滚后仍产生一条成功通知。

Kafka 发送并不会因为发生在 @Transactional 方法里，就自动加入普通 JDBC 事务。MySQL 回滚也无法把已经进入 Kafka 的消息撤回来。因此，需要把“记下需要通知这件事”和“实际发送通知消息”拆开。

Outbox 先把待发送事件和业务一起保存 ​

Outbox 是存放待发送事件的数据库表。业务事务除了更新业务数据，还插入一条事件记录：

text
事务一：HTTP 请求线程
  修改申请状态
  增加项目成员
  插入 Outbox，状态为 PENDING
  → 一起提交或一起回滚

后台 Relay
  读取待发送事件 → 发送 Kafka → 收到确认后标记 SENT

消费者
  读取 Kafka → 写通知数据库 → 提交消费进度

一条最小事件记录可以包含稳定的 event_id、事件类型、版本、正文和投递状态。消息正文保存处理通知所需的数据快照，让后续处理不必重新猜测业务发生时的内容。多次重试同一条事件，应继续使用同一个事件标识。

java
@Transactional
public void approve(ApproveCommand command) {
    applicationMapper.markApproved(command.applicationId());
    memberMapper.insert(buildMember(command));
    outboxMapper.insert(buildPendingEvent(command));
}

这里的关键是三个操作使用同一个本地事务。Outbox 写入失败时，业务也不能当作整体成功；业务提交成功后，数据库中则留下一条可供后台继续处理的待办。

发送确认和 SENT 状态之间仍可能重发 ​

Relay 可以定时扫描 PENDING 事件。多个工作者并发时，需要通过合适的锁定或领取机制避免无序争抢。学习示例可以在事务中锁定一条记录、发送并等待确认，再更新状态，但网络等待期间会占用数据库连接和锁；吞吐需求上来后，应重新评估领取状态、租约和批量处理设计。

即使做了这些，仍存在一个时间窗口：Kafka 已确认收到消息，Relay 却在提交 SENT 之前停止。恢复后，数据库中该事件仍是待发送状态，于是会再次发送。

enable.idempotence=true 能约束生产者协议层面的特定重试重复，不能代替跨进程重启、跨数据库状态更新的业务去重。稳定的 Kafka 消息 key 也不意味着 Broker 会按这个 key 自动删除重复事件。

因此，这类设计应准备接收重复事件。Outbox 缩小了丢失待发送意图的窗口，但不等于端到端“恰好执行一次”。SENT 也只说明发送得到确认并记录了结果，不代表通知已经落库或被用户读到。

先提交通知数据库，再提交 Offset ​

消费者需要在业务处理完成后确认消费进度。以下片段只演示单条、顺序处理的提交顺序；saveIdempotently 应在事务提交后才返回：

java
notificationWriter.saveIdempotently(event);

TopicPartition partition =
    new TopicPartition(record.topic(), record.partition());
consumer.commitSync(Map.of(
    partition, new OffsetAndMetadata(record.offset() + 1)
));

显式管理进度时需关闭自动提交。提交的位置表示下次应读取的位置，因此处理完某条记录后，通常提交该记录的 offset + 1。批量或并行处理时，必须按分区确认连续完成的位置，不能因为后面的记录处理成功，就越过前面尚未成功的记录。

若先提交 Offset，再写数据库，崩溃可能使未完成的通知被跳过。反过来先写数据库，则可能在数据库提交后、Offset 提交前崩溃，恢复时重复处理。这正是消费者必须具备业务幂等的原因。

一种做法是为事件标识设置唯一约束，并在同一数据库事务内完成去重记录和通知写入。遇到重复时，应确认是预期事件已经成功处理；其他数据库异常不能一概吞掉，也不要因重试覆盖原通知的已读状态。处理失败后还需明确重试、暂停或恢复策略，不能在内存读取位置已经前移后直接继续跳过错误记录。

AFTER_COMMIT 保证执行时机，不提供持久化队列 ​

@TransactionalEventListener(phase = AFTER_COMMIT) 可以让监听器在业务事务成功提交后执行；默认没有事务时不会执行，除非启用 fallbackExecution。它适合表达“只有提交成功才做后续动作”。

但进程可能在数据库提交后、监听逻辑完成前停止，内存中的事件不会自动变成可恢复的待办。监听器也不会仅凭这个注解自动异步执行。若提交后还要写数据库，应通过适当的新事务边界执行，例如调用另一个 Bean 中声明 REQUIRES_NEW 的方法。

当需求进一步要求应用重启后仍可重试投递时，Outbox 才承担持久记录发送意图的职责。最终能否持续送达，还取决于 Relay 恢复、消费者故障处理、消息保留时间和运行监测等配套机制，不能由一张表或一个注解单独保证。
