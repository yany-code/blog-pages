14 · LangGraph 高级特性 ​

以下保留原学习资料的章节结构与版本语境；示例依赖对应环境，接入真实项目时需按所用版本配置。

迁移校订

  • 动态 interrupt 通常使用 Command(resume=...) 恢复，不能将 invoke(None) 泛化为所有中断的恢复方式。节点恢复可能重放 interrupt 前的代码；真实外部调用需设计幂等与明确的执行边界。流模式、存储和子图行为仍需按版本验证。

章节定位：前面章节我们构建的 Graph 多数是“一次性、内存态、全自动”的玩具雏形。本章的五大高级特性是 LangGraph 成为工业级 Agent 基础设施的真正分水岭：它解决了“进度不可见、故事不能续、关键动作不能让人放行、出错了无法回溯、图太大无法拆分”等所有真实生产痛点。

核心架构图：五大特性的生产协同链路 ​

模块一：流式处理（Streaming）—— 拆解图的黑盒 ​

1、核心差异：LLM 流式 vs LangGraph 流式 ​

  • 普通 LLM 流式：仅解决“模型生成的 Token 如何逐字输出”，本质是单个文本片段流。
  • LangGraph 图流式：把整张图的执行过程全景展开——当前走到哪一步、那一步改了哪些字段、业务进度百分比、以及模型打字机片段，全部统一分发。

2、五大stream_mode对比 ​

模式返回内容典型场景
values节点执行完毕后的当前完整状态快照监控整张图的最终宏观全貌
updates节点执行完毕后本步骤改动的增量字段（Diff）节点级调试、前端增量补丁更新
messagesLLM 生成的实时消息片段/Token块对话前端实现打字机效果
custom节点内部主动写出的业务数据（进度百分比、日志）展现“正在搜索知识库（30％）”等UI反馈
debug框架底层执行轨迹（调度、执行器耗时等）深度排查图引擎调度瓶颈

3、自定义流（custom）最佳实践 ​

在节点内通过get_stream_writer()注入自定义事件：

python
from langgraph.config import get_stream_writer

def search_node(state: State):
	writer = get_stream_writer()
	# 业务进度主动推送（不会污染 State）
	writer({"step": "search", "progress": "50％", "msg": "正在向量数据库中做相似度检索..."})
	# 状态数据正常返回
	return {"results": ["doc1", "doc2"]}

# 客户端组合监听：同时消费增量状态和自定义进度
for mode, payload in graph.stream(inputs, stream_mode=["updates", "custom"]):
	if mode == "custom":
		print(f"[进度提示]: {payload['msg']}")
	elif mode == "updates":
		print(f"[节点完成]: {payload}")

模块二：状态持久化（Persistence）—— 智能体的记忆根基 ​

1、Checkpointer 与 thread_id 的本质 ​

  • thread不是线程 ID：它是状态空间的命名隔离键。一个thread_id代表一个独立的对话线程或任务示例。
  • 增量存档机制：每个节点执行完毕（Superstep 完成）后，Checkpointer 会对当前状态做一次原子落盘，生成一个checkpoint_id。

2、双层记忆架构：Checkpointer vs BaseStore ​

绝对不要混淆两者职责：

  • Checkpointer（短期会话状态）：保存当前这根线（Thread） 里的运行状态与历史快照。用于断点续跑、会话内连续对话、人机审核挂起。
  • Store / BaseStore（长崎跨会话记忆）：保存跨越所有 Thread 的全局事实（例如用户的个人习惯、VIP等级、跨对话积累的背景知识）。

3、断点恢复：神奇的invoke(None) ​

当系统崩溃或网络断开后，无需让整个工作流重新跑一遍（避免重复花钱和副作用）：

python
# 传入 None，告知图引擎：不要从 START 初始化，而是加载该 thread 最近的一个 checkpoint 继续跑！
graph.invoke(None, config={"configurable":{"thread_id": "order-task-9527"}})

4、存储后端演进选型 ​

  1. InMemorySaver: 进程内字典，单机测试用，进程重启即丢。
  2. SqliteSaver(langgraph-checkpoint-sqlite): 本地单文件数据库，适合单机部署、轻量 Agent。
  3. PostgresSaver(langgraph-checkpoint-postgres): 生产级高并发推荐，支持严格事务、高可用与长期归档。

模块三：人机协作（HITL）—— 关键动作的“保险栓” ​

生产环境中，转账、删库、批量发邮件、下单扣款 等高位动作绝不能完全相信大模型的自主判断。

1、interrupt与Command(resume=...)原语 ​

2、最小实现范式 ​

python
from langgraph.types import Command, interrupt

def transfer_review_node(state: State):
    # 1. 触发打断，向外部暴露审核 Payload，当前线程在此挂起
    user_decision = interrupt({
        "action": "transfer",
        "to": state["target_account"],
        "amount": state["amount"]
    })
    # 2. 外部恢复后，user_decision 拿到外部 resume 传进来的字典
    return {"is_approved": user_decision["approved"], "final_amount": user_decision["amount"]}

# 第一次调用：执行到 interrupt 处自动中断退出
graph.invoke(initial_data, config=thread_cfg)

# 审核员审批后，通过 Command(resume=...) 唤醒
graph.invoke(Command(resume={"approved": True, "amount": 80}), config=thread_cfg)

致命陷阱：重放幂等性问题 当图被唤醒恢复时，包含interrupt的节点函数会从第一行“重新执行一遍”，直到执行到interrupt行才拿到 resume 值继续向下！

  • 绝对禁忌：千万不要在interrupt前面编写非幂等的真实外部调用（如send_email()、charge_credit_card()，否则每次恢复都会被重复触发！
  • 推荐解法：在review_node里只负责组装审核参数；真正的扣款、发信动作，放到审核通过后的下一个独立节点execute_action_node中执行。

模块四：事件回溯（Time-Travel）—— 探索平行宇宙 ​

由于LLM的非确定性，当 Agent 在第 5 步跑偏时，如果全量重跑，前4步可能又产生新变数。事件旅行运行我们会到确定的历史检查点，修正变量，分叉探索。 标准四步操作法

python
# 1. 查询该线程下的全部历史快照（时间倒序）
history = list(graph.get_state_history(config))

# 2. 挑选出出问题的那个历史快照 checkpoint_config
target_snapshot = history[2]
target_cfg = target_snapshot.config

# 3. （可选）修改该检查点的状态数据，生成新分叉起始点
new_cfg = graph.update_state(
    target_cfg,
    values={"user_intent": "修正后的真实意图"}
)

# 4. 从分叉点开启全新分支执行，原历史记录不受破坏
new_result = graph.invoke(None, new_cfg)

模块五：子图（Subgraphs）—— 复杂图的组件化封装 ​

当图超过 10 个节点时，单图编排会导致代码混乱、测试困难。子图让你可以像抽取 Python 函数一样抽取独立图。 三种集成模式演进

生产首选：代理节点适配器模式（模式3） 父图与子图往往由不同团队开发，状态 Schema 必然不同，直接强行融合会导致字段污染：

python
# 代理节点：负责父子图之间的“适配器 (Adapter)”转换
def call_subgraph_proxy(parent_state: ParentState) -> dict:
    # 1. 结构转换：从父状态提取子图所需的输入
    sub_input = {"analysis_input": parent_state["user_query"]}

    # 2. 运行子图
    sub_output = compiled_subgraph.invoke(sub_input)

    # 3. 结构逆转换：把子图产出的专业分析，映射回父图的业务字段
    return {"final_answer": sub_output["analysis_result"]}

# 在父图里，该代理函数就像普通节点一样挂载
parent_builder.add_node("analysis_proxy", call_subgraph_proxy)
