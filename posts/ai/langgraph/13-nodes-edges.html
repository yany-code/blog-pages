13 · LangGraph API：节点、边与进阶 ​

以下保留原学习资料的章节结构与版本语境；示例依赖对应环境，接入真实项目时需按所用版本配置。

模块一：Node（节点）核心规范与健壮性 ​

1、节点的本质与参数规范 ​

节点本质就是一个 Python 函数。在 LangGraph 中，节点签名遵循以下原则：

python
from langgraph.types import Runtime
from langchain_core.runnables import RunnableConfig

def my_node(state: MyState, config: RunnableConfig, runtime: Runtime) -> dict:
	# 1. state: 核心业务数据流（必须）
	# 2. config：包含 thred_id、callbacks、tags、metadata 等（可选）
	# 3. runtime：包含静态上下文 context、stream_writer 等（可选）

	# 建议返回本节点修改的字段（Partial State）；已有 reducer 的字段应按其合并规则返回
	return {"key_to_update": "new_value"}

黄金法则：单一职责原则 一个 Node 只做一件事（例如：仅清晰输入、或仅请求大模型、或仅格式化结果）。避免把“大模型生成 + 提取参数 + 调用外部数据库”塞进同一个 Node，否则会导致状态回溯困难、无法单独重试、打断点测试失效

2、节点级容灾：RetryPolicy（重试策略） ​

大模型 API 偶发超市、网络波动是生产常态。直接在业务代码里手写try...except...while会严重污染逻辑，LangGraph 支持声明式重试策略：

python
from langgraph.types import RetryPolicy

# 为特定易波动节点挂载重试规则
workflow.add_node(
    "llm_node",
    call_llm_node,
    retry_policy=RetryPolicy(
        max_attempts=3,          # 最大重试次数
        backoff_factor=2.0,      # 指数退避乘数（1s -> 2s -> 4s）
        initial_interval=1.0,    # 初始等待时间（秒）
        retry_on=Exception       # 触发重试的异常类型
    )
)

3、算力节约：CachePolicy（节点级缓存） ​

对于消耗昂贵 Token 或耗时极长且输入幂等的节点（例如：静态长文本特征提取、外部重检索），可以开启节点级缓存：

python
from langgraph.types import CachePolicy
from langgraph.cache.in_memory import InMemoryCache

# 1. 绑定缓存策略
workflow.add_node(
    "expensive_extract_node",
    heavy_llm_task,
    cache_policy=CachePolicy(
        ttl=3600,  # 缓存 1 小时
        # 也可传入 key_func 自定义哈希 key 提取逻辑
    )
)

# 2. 编译图时必须注入 Cache 存储后端
app = workflow.compile(cache=InMemoryCache())

模块二：Edge（边）与控制流拓扑 ​

边决定了计算图的数据流和生命周期。

1、三种基本拓扑边对比 ​

边的类型API 语法触发时机与用途适用场景
普通边 (Normal)add_edge("A", "B")A 执行完毕后，无条件直接流转到 B固定流水线、顺序处理
条件边 (Conditional)add_conditional_edges("A", route_fn, path_map)A 执行完毕后，调用 route_fn(state) 根据状态返回值查表跳转分支判断、校验通过/失败路由
条件入口 (Entry)add_conditional_edges(START, route_fn, path_map)图一启动立即路由，不经过任何前置普通节点根据用户 Intent 直接分流到不同子链路
典型条件边写法：
python
def check_route(state: AgentState) -> str:
    if state.get("is_valid"):
        return "approved"
    return "rejected"

# path_map 显式声明路由去向，有助于编译期静态检查与可视化渲染
workflow.add_conditional_edges(
    "validator_node",
    check_route,
    {
        "approved": "generate_report_node",
        "rejected": "send_alert_node"
    }
)

2、有向环（Cyclic Graph）与死循环熔断 ​

智能体（Agent）区别于普通工作流的核心在于循环（Loop）： 只要条件边存在指回上游节点的路径，图就构成了有向环。

生产防护：死循环熔断保障 在有环图中，若 LLM 陷入逻辑死循环或工具反复报错，图会一直执行直至耗尽 Token。必须设置最大执行步数：

python
# 限制整张图单次运行的最大超步（Superstep）数量
app.invoke(
    {"input": "xxx"},
    config={"recursion_limit": 50}  # 默认 25，生产建议严格限制
)

超过限制后系统会直接抛出GraphRecursionError，确保系统不会失控

模块三：进阶散发控制原语（Send，Command，Runtime） ​

这是 LangGraph 区别于初级流编排框架的“分水岭能力”

1、Send：动态并行扇出（Map-Reduce） ​

  • 痛点：传统的 add_edge 只能定义固定的拓扑。如果前置节点动态拆解出 NNN 个待处理任务（NNN 是未知的运行时动态值），该如何并发处理？
  • 解法：Send(node_name, state_payload) 允许条件边函数返回一个 Send 对象列表，LangGraph 会在同一个 Superstep 中并发拉起多个独立的目标节点实例！
python
from langgraph.types import Send
from typing import List

# 状态中具有 tasks: ["子任务A", "子任务B", "子任务C"]
def fan_out_tasks(state: MainState) -> List[Send]:
    return [
        Send("worker_node", {"task_item": item, "worker_id": idx})
        for idx, item in enumerate(state["tasks"])
    ]

# 声明动态扇出条件边
workflow.add_conditional_edges("planner_node", fan_out_tasks, ["worker_node"])
workflow.add_edge("worker_node", "aggregator_node")

2、Command：原子更新于动态跳转（State Update + Goto） ​

  • 痛点：在传统方案中，若要在节点内做判断，必须先“由节点更新状态”，再“写一个外部路由函数查状态做跳转”。代码割裂且无法把局部控制逻辑封装在节点内。
  • 解法：Command 将 “状态更新（update）” 与 “下一步去向（goto）” 封装在单一返回值中！
python
from typing import Literal
from langgraph.types import Command
from langgraph.graph import END

def decision_node(state: State) -> Command[Literal["human_review", "publish_node", END]]:
    confidence = state["score"]

    if confidence > 0.9:
        # 同时修改状态，并指定直接跳到 publish_node
        return Command(update={"status": "auto_pass"}, goto="publish_node")
    elif confidence > 0.5:
        # 指向人工审核
        return Command(update={"status": "need_review"}, goto="human_review")
    else:
        # 直接结束
        return Command(update={"status": "rejected"}, goto=END)

# 挂载了 Command 的节点，不再需要额外的 add_conditional_edges！
workflow.add_node("decision", decision_node)

何时有限使用Command？

  1. 多智能体路由器（Multi-Agent Router）：路由决策由 LLM 在节点内完成，决定把请求直接转达给特定的 Agent。
  2. 人机协同（Human-in-the-loop）：中断恢复时，通过Command)resume=..., goto=...)无缝恢复执行链。

3、Runtime Context：静态配置与动态状态解耦 ​

  • 核心哲学：
    • State（业务状态）：随执行不断累加、需要被持久化保存到 Checkpointer、属于当前对话的上下文。
    • Context（运行环境）：数据库连接池、外部 API Key、租户配置、权限信息，绝对不应被序列化存进数据库。
  • 实现方案：通过 context_schema 隔离注入。
python
from typing import TypedDict
from langgraph.graph import StateGraph
from langgraph.types import Runtime

# 1. 定义静态上下文 Schema
class AppContext(TypedDict):
    tenant_id: str
    db_session: object
    admin_api_key: str

# 2. 图定义时指定 context_schema
workflow = StateGraph(state_schema=UserState, context_schema=AppContext)

# 3. 节点通过 runtime.context 优雅调用静态依赖
def query_node(state: UserState, runtime: Runtime[AppContext]):
    tenant = runtime.context["tenant_id"]
    db = runtime.context["db_session"]
    # 纯只读使用，不会污染持久化的 state
    data = db.find(tenant_id=tenant, user=state["user_id"])
    return {"query_result": data}

app = workflow.compile()

# 4. 执行时传入 context（每次调用可不同）
app.invoke(
    {"user_id": "U1001"},
    context={"tenant_id": "T888", "db_session": db_client, "admin_api_key": "sk-xxx"}
)
