08 · RAG 检索增强生成 ​

以下保留原学习资料的章节结构与版本语境；示例依赖对应环境，接入真实项目时需按所用版本配置。

迁移校订

  • RAG 不能保证消除幻觉。代码是依赖前置 vectorstore 和 model 的管道片段；实际应用应显式格式化检索正文与来源，并分别验证检索命中、回答及引用。

1、什么是 RAG？ ​

  • 定义: RAG（Retrieval-Augmented Generation, 检索增强生成） 是一种 "先检索外部资料, 在带着资料发问" 的经典架构。
  • 通俗比喻:
    • 直接问大模型 = "闭卷考试"（仅凭模型自身训练参数里的记忆, 容易遗忘私有制度、产生胡编乱造的"幻觉"）;
    • RAG 架构 = "开卷考试"（遇到问题先翻阅企业知识库, 把找到的参考条款放到桌面上, 再让模型照着资料答题）。
  • 核心价值: 低成本引入私有知识、实时动态更新、答案有据可查课追溯、减少缺乏依据的回答，但仍需核验检索与生成结果。

2、RAG 经典两阶段全景架构（必背） ​

RAG 系统在工程上被严格划分为离线索引与在线问答两个完全解耦的阶段:

3、核心组件与流水线拆解 ​

3.1、基础数据单元: Document ​

LangChain 中所有文档在内存中的统一定义:

python
Document(
	page_content="正文内容文本...",    # 真正参与 Embedding 计算和送给模型的部分
	metadata={"source": "faq.docx", "page": 2, "category": "售后"} # 负责展示来源、权限过滤
)

3.2、文档加载器（Document Loaders） ​

屏蔽不同文件底层格式的差异, 统一输出List[Document]:

  • PDF: PyPDFLoader
  • Word: Docx2txtLoader（轻量稳定）/ UnstructureWordDocumentLoader
  • Markdown / TXT: UnstructuredMarkdownLoader / TextLoader
  • 加载方式: 小文件用.load()（一次性全部读入内存）; 海量大文件用.lazy_load()（生成器流式懒加载）。

3.3、文本分割器（Text Splitters / Chunking） ​

  • 为什么要切块?
    • 文档太长直接塞进模型: 昂贵费用、超出窗口限制, 且关键语义被海量废话稀释;
    • 整篇文档做Embedding: 向量包含信息太杂, 很难精确匹配细碎问题。
  • 通用最佳实践: RecursiveCharacterTextSplitter（递归字符分割器）
    • 核心参数:
      • chunk_size: 单块最大字符长度（常用 300 ~ 800 字符）;
      • chunk_overlap: 相邻块的前后重置长度（通常取chunk_size的10％）。
    • 重叠（Overlap）的意义: 防止语义正好在句中被"拦腰截断", 保证上下文连贯！

4、经典代码: LCEL 一行流 RAG 管道（✨核心标准范式） ​

使用学过的 LCEL 管道符, 把检索器、提示词和模型串成全自动问答链

python
from langchain_core.prompts import PromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

# 1. 检索器（由向量库导出）
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# 2. 防幻觉约束 Prompt
template = """你是一名专业的智能知识库助手。请根据以下参考资料回答用户问题。
如果参考资料中没有相关信息，请直接回答"知识库中未找到相关依据"，绝对禁止自行推测编造！

【参考资料】：
{context}

【用户问题】：
{question}
"""
prompt = PromptTemplate.from_template(template)

# 3. 核心：优雅的 LCEL RAG 流水线
rag_chain = (
    # 并行分流：question 原样透传给 Prompt，同时送入 retriever 查出 context
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)

# 4. 一键问答
answer = rag_chain.invoke("错误码 A0001 代表什么含义？")
print(answer)

RunnablePassthrough的精妙之处: 用户输入问题时, 它做到了"一分为二" —— 一路传给检索器去搜资料, 另一路原样保留作为{question}, 最后一起注入 Prompt ！

5、从管道式 RAG 到企业生产级五维优化 ​

初级 RAG（Naive RAG）往往面临"查不准、召不全、答不对"的问题。企业生产级系统通常从以下 5 个维度全面升级:

  1. 查询侧（Query Rewrite）：用户提问往往太简略（如“怎么退？”），先用大模型改写为语义完整的问句（“平台售后订单如何申请全额退款流程”）。
  2. 检索侧（混合检索 Hybrid Search）：
    • 向量检索 解决“语义相似、换个说法也能懂”；
    • BM25 关键词检索 解决“错误码、型号、专业名词不能写错”；
    • 二者结合，互补短板。
  3. 排序侧（重排序 Rerank）：
    • 第一阶段粗筛召回 Top-20；
    • 用专门的精排模型（如 BGE-Reranker）精打细分，只挑最权威的 Top-3 喂给大模型，大幅减少干扰与 Token 消耗。
  4. 架构升级（Agentic RAG）：
    • 管道式 RAG（本章）：每次提问必须先死板地检索一次；
    • Agent 式 RAG（后续第 21 章）：由大模型自主判断“这个问题需不需要查知识库？需要查哪个库？查一次不够要不要换关键词再查一次？”。

💡 核心考点与背诵口诀 ​

  1. RAG 核心就两步：离线建库把索引做，在线问答先搜后答。
  2. 统一数据叫 Document：正文放 page_content，来源属性归 metadata。
  3. 文本切块有讲究：首选 Recursive，单块大小定 chunk_size，语义不断靠 overlap。
  4. LCEL 串联精气神：{"context": retriever, "question": RunnablePassthrough()} | prompt | model。
  5. 防假防幻靠 Prompt：资料没有明直说，严禁瞎猜与胡诌。
