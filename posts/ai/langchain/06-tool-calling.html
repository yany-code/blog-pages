06 · Tool Calling 与 Function Calling ​

以下保留原学习资料的章节结构与版本语境；示例依赖对应环境，接入真实项目时需按所用版本配置。

1、工具调用的分工边界（必背） ​

所有工具调用的底层逻辑, 都建立在这一条不可动摇的黄金法则之上:

模型负责决策, 程序负责执行!

  • 大模型负责: 理解用户意图, 判断"要不要调工具、调哪个工具、传什么参数"(产出结构化意图);
  • 你的 Python 程序负责: 真正去发 HTTP 请求、查数据库、算公式, 并把运行结果再喂回给大模型。
  • ❗模型绝对不会自己在云端跑你的 Python 代码或私有网络请求!

2、Tool vs Tool Calling vs Agent vs MCP ​

初学者最容易混淆这几个词, 一句话厘清本质:

概念它是什么通俗比喻核心职责
Tool被包装好的一个外部函数/能力螺丝刀、计算器、天气 API负责**“做具体的事”**
Tool Calling模型输出结构化调用意图的协议报出“我要用 10 号扳手拧这颗螺丝”负责**“发起调用请求”**
Agent具备自主规划、会循环做决策的智能体拿着工具箱的修理工负责**“决定先用哪个、后用哪个、是否继续”**
MCP开放模型上下文协议（第 20 章）统一的 USB / Type-C 接口负责**“让外部工具能以统一标准接入任何模型”**

3、工具调用的 7 步生命周期与消息闭环 ​

工具调用依然发生在消息流中, 整个闭环由 3 个关键消息对象驱动: 关键消息三剑客（必须对齐）

  • AIMessage.tool_calls: 模型的**"请假条/调用请求"** （包含工具名、参数字典、唯一的tool_call_id）。
  • ToolMessage: 程序的**"审批回执/执行结果"** （必须回填相同的tool_call_id, 告诉模型这里回答刚才哪一次调用的）。

4、如何定义一个 Toll? （两级演进范式） ​

4.1、基础级: @tool 装饰器 + Docstring （快速原型） ​

LangChain 中最轻量的定义方式。Docstring 就是给模型看的 Prompt!

python
from langchain_core.tools import tool

@tool
def add_numbers(a: int,b: int) -> int:
	"""计算两个整数的加法求和"""
	return a + b

# 查看 LangChain 自动生成的元数据
print(add_numbers.name)        # add_numbers
print(add_numbers.description) # 计算两个整数的加法求和
print(add_numbers.args)        # {'a': {'type': 'integer'}, b: {'type': 'integer'}}

4.2、企业生产级: @tool(args_schema=PydanticModel)（✨核心推荐） ​

函数签名能表达的信息太少。真实业务必须搭配 Pydantic, 实现:

  1. 给模型看: 详细字段说明（Field(description)）, 降低大模型幻觉与参数填错率;
  2. 给程序看: 运行时类型强校验（自动拦截非法参数）。
python
from pydantic import BaseModel, Field
from langchain_core.tools import tool

# 1. 定义严谨的参数契约（Schema）
class WeatherQueryInput(BaseModel):
	location: str = Field(description="城市英语拼音或英文名, 如 Beijing、Shanghai")
	unit: str = Field(default="metric", description="温度单位: metric（摄氏度）或 imperial（华氏度）")

# 2. 绑定参数模型
@tool(args_schema=WeatherQueryInput)
def get_current_weather(location: str, unit: str = "metric") -> str:
	"""查询指定城市的实时天气数据"""

5、绑定工具: model.bind_tools() ​

定义好工具后, 大模型默认是不知道的。必须先执行绑定声明:

python
# 告诉模型: 你现在拥有了调用这几个工具的能力
model_with_tools = model.bind_tools([add_numbers, get_cuurent_weather])

# 此时调用模型，如果问题涉及天气，模型会自动输出 tool_calls 而不是直接编造答案
response = model_with_tools.invoke("北京现在冷不冷？")
print(response.tool_calls)

# 输出: [{'name': 'get_current_weather', 'args': {'location': 'Beijing', 'unit': 'metric'}, 'id': 'call_123...'}]

❗注意: bing_tools 只是把工具的 名称、说明、参数结构（JSON Schema） 声明给了模型, 并没有真正执行工具！

6、生产级工具设计的 6 大工程军规 ​

在真实商业项目（如金额、客服、电商）中, Tool 设计往往决定了系统的生死:

  1. Docstring 就是系统提示词：不要只写“查数据”，要写清“什么时候该调、入参的枚举值、边界情况”。
  2. 职责单一（Single Responsibility）：一个工具只做一件事，不要把“查询 + 扣费 + 发邮件”揉在一个 Tool 里。
  3. 副作用隔离（读写分离）：
    • 只读工具（Safe）：查天气、搜向量库、读订单，可放开让模型自由调用。
    • 有副作用工具（Mutating）：转账、删库、退款、下单，必须在程序端增加**人工二次确认（Human-in-the-loop）**或严格的鉴权拦截！
  4. 输出稳定可控：返回给模型的工具结果，尽量是清洗过的简练 JSON 或文本，不要把几万行的无用 HTML/原生堆栈全扔给模型，避免撑爆 Token 上下文。
  5. 异常优雅捕获：API 报错时，不要直接让 Python 崩溃，捕获后返回友好文本（如 {"error": "城市名不存在，请核对拼写"}），大模型读到错误信息后甚至会自我纠错重新提问！
  6. 防死循环与限流：配置超时时间（timeout）与单次会话最大工具调用步数限制。

💡 核心考点与背诵口诀 ​

  1. 分工原则牢记心：模型只管下命令，执行全靠 Python 跑。
  2. 定义工具两步走：基础用 @tool，企业必须上 Pydantic 参数 Schema。
  3. 模型开眼靠绑定：bind_tools 传入工具列表，模型才识乾坤。
  4. 消息回传认准 ID：模型发起看 tool_calls，程序交差回填 ToolMessage。
  5. 工具是手脚，记忆是便签，Agent 是大脑。
