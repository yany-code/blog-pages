〇、核心结论 ​

  • 现在就可以开工：接口契约（路由、参数、响应结构、错误码）已在文档中冻结，前端不依赖后端代码全部完成；未实现的接口用 mock 顶上，后端每完成一个阶段替换一批。
  • 技术选型：Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus + axios。 （React + Antd 是等价替代，本文的分层架构、请求封装、阶段规划对两种栈同样适用；选 Vue 是因为模板语法对 Java 背景最友好、国内生态资料多。）

二、基础设施（一次写对，所有页面受益） ​

这是整个前端最值得花功夫的部分，写完之后每个页面只剩"调 api + 渲染数据"。

2.1 与后端契约对应的类型 ​

ts
// src/types/api.ts —— 与 docs/api接口库.md 2.2 节一一对应
export interface ApiResponse<T> {
  code: number      // 0=成功；40000/40100/40300/40400/40900/42900/50000
  message: string
  data: T
  traceId: string   // 排查问题时带上报后端
}

export interface PageResult<T> {
  list: T[]
  page: number
  pageSize: number
  total: number
}

// src/types/auth.ts —— 与后端 TokenVO/RegisterDTO 对应
export interface TokenVO { tokenType: string; accessToken: string; refreshToken: string; expiresIn: number }
export interface LoginDTO { username: string; password: string }
export interface RegisterDTO { username: string; password: string; nickname: string; phone?: string; email?: string }

注意：后端 Jackson 配了 non_null，值为 null 的字段会整个缺失而不是 "x": null，读取一律用可选链 data?.xxx。

2.2 Token 存储（用户端与管理端分开） ​

ts
// src/utils/token.ts
function createTokenStorage(prefix: string) {
  return {
    getAccess: () => localStorage.getItem(`${prefix}.access`),
    getRefresh: () => localStorage.getItem(`${prefix}.refresh`),
    set: (access: string, refresh: string) => {
      localStorage.setItem(`${prefix}.access`, access)
      localStorage.setItem(`${prefix}.refresh`, refresh)
    },
    clear: () => {
      localStorage.removeItem(`${prefix}.access`)
      localStorage.removeItem(`${prefix}.refresh`)
    },
  }
}

export const userTokens = createTokenStorage('yuki.user')
export const adminTokens = createTokenStorage('yuki.admin') // 管理后台单独一套，互不干扰

学习项目存 localStorage 即可；理解 XSS 风险后可升级为「refresh 存 httpOnly cookie」——那需要后端配合改接口，现阶段不做。

2.3 axios 封装（本项目最关键的一段代码） ​

后端有四个约定直接决定了这个封装怎么写：

  1. 业务错误也是 HTTP 200，只能看 body 里的 code；
  2. 请求头要带 Authorization: Bearer <token>；
  3. 40100 时可用 refreshToken 换新（刷新会轮换，两个 token 必须同时替换）；
  4. 失败响应里有 traceId，要能带到用户眼前。
ts
// src/utils/request.ts
import axios from 'axios'
import type { ApiResponse } from '@/types/api'
import { userTokens } from '@/utils/token'
import { userStore } from '@/stores/user'

export class ApiError extends Error {
  constructor(public code: number, message: string, public traceId?: string) {
    super(message)
  }
}

export const http = axios.create({ baseURL: '/api/v1', timeout: 10000 })

http.interceptors.request.use((config) => {
  const token = userTokens.getAccess()
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 单飞刷新：并发多个 40100 只发一次 refresh 请求
let refreshing: Promise<boolean> | null = null

async function tryRefresh(): Promise<boolean> {
  if (!userTokens.getRefresh()) return false
  refreshing ??= doRefresh().finally(() => (refreshing = null))
  return refreshing
}

async function doRefresh(): Promise<boolean> {
  try {
    // 用裸 axios，避免走自己的拦截器造成递归
    const res = await axios.post<ApiResponse<{ accessToken: string; refreshToken: string }>>(
      '/api/v1/auth/refresh', { refreshToken: userTokens.getRefresh() })
    if (res.data.code !== 0) throw new Error(res.data.message)
    // 轮换语义：旧 refresh 已作废，两个 token 必须原子地一起换
    userTokens.set(res.data.data.accessToken, res.data.data.refreshToken)
    return true
  } catch {
    userTokens.clear()
    userStore.logoutLocal()          // 清 Pinia 状态
    return false
  }
}

http.interceptors.response.use(async (res) => {
  const body = res.data as ApiResponse<unknown>
  if (body.code === 0) return body.data as never   // 成功：直接解包 data，调用方拿到的就是业务数据

  if (body.code === 40100 && !res.config._retried) {
    // 未登录/过期：尝试刷新后重放一次原请求
    if (await tryRefresh()) {
      res.config._retried = true
      return http.request(res.config) as never
    }
    userStore.redirectToLogin()
  }
  return Promise.reject(new ApiError(body.code, body.message, body.traceId))
})
ts
// 为 TS 声明自定义字段
declare module 'axios' {
  interface InternalAxiosRequestConfig { _retried?: boolean }
}

使用效果：页面里 try { const me = await userApi.me() } catch (e) { if (e instanceof ApiError) ElMessage.error(${e.message} (${e.traceId})) }——错误码、traceId 全都不用散落在业务代码里处理。

2.4 金额工具（严禁 Number 相加） ​

后端金额是字符串 "99.90"，为避免浮点误差，前端计算一律转"分"（整数），展示再格式化回来：

ts
// src/utils/money.ts
export function toCents(amount: string): number {
  const [yuan, fen = ''] = amount.split('.')
  return Number(yuan) * 100 + Number(fen.padEnd(2, '0').slice(0, 2))
}

export function formatCents(cents: number): string {
  const sign = cents < 0 ? '-' : ''
  const abs = Math.abs(cents)
  return `${sign}${Math.floor(abs / 100)}.${String(abs % 100).padStart(2, '0')}`
}

// 购物车合计：list.reduce((sum, i) => sum + toCents(i.price) * i.quantity, 0) → formatCents()

2.5 幂等键 ​

创建订单、发起支付必须携带 Idempotency-Key 请求头。同一次"下单意图"重试时必须复用同一个 key，否则重试会被当成新订单：

ts
// src/utils/idempotency.ts
// 在"点击下单"那一刻生成并暂存，请求成功/离开页面后清除
let current: string | null = null
export function takeIdempotencyKey(): string {
  if (!current) current = crypto.randomUUID()
  return current
}
export function clearIdempotencyKey() { current = null }

在下单 api 函数里挂上：http.post('/orders', body, { headers: { 'Idempotency-Key': takeIdempotencyKey() } })，成功回调里 clearIdempotencyKey()。

三、状态管理与路由 ​

3.1 用户 store ​

ts
// src/stores/user.ts
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'
import type { UserVO } from '@/types/user'
import { userApi } from '@/api/user'
import { authApi } from '@/api/auth'
import { userTokens } from '@/utils/token'
import { LoginDTO, RegisterDTO, TokenVO } from '@/types/auth'

export const useUserStore = defineStore('user', () => {
  const profile = ref<UserVO | null>(null)
  const isLogined = computed(() => !!userTokens.getAccess())

  async function login(dto: LoginDTO) {
    const token: TokenVO = await authApi.login(dto)
    userTokens.set(token.accessToken, token.refreshToken)
    profile.value = await userApi.me()
  }
  async function register(dto: RegisterDTO) {
    const token = await authApi.register(dto)   // 注册即登录
    userTokens.set(token.accessToken, token.refreshToken)
    profile.value = await userApi.me()
  }
  async function loadProfile() {
    profile.value = isLogined.value ? await userApi.me() : null
  }
  function logoutLocal() { userTokens.clear(); profile.value = null }
  async function logout() { logoutLocal() } // 后续后端加登出接口时在此补调用
  return { profile, isLogined, login, register, loadProfile, logoutLocal, logout }
})

守卫做两件事：没登录跳登录页（记录 redirect 以便登录后跳回）；刷新页面后首次进登录区时拉一次 /users/me 恢复资料。

ts
router.beforeEach(async (to) => {
  const user = useUserStore()
  if (to.meta.requiresAuth && !user.isLogined) {
    return { path: '/login', query: { redirect: to.fullPath } }
  }
  if (to.meta.requiresAuth && !user.profile) {
    try { await user.loadProfile() } catch { return { path: '/login' } }
  }
  // requiresAdmin 区域：用 adminTokens 的存在性做 UI 级判断；真正的权限由后端 40300 兜底
  if (to.meta.requiresAdmin && !adminTokens.getAccess()) return { path: '/admin/login' }
})

管理员是否"超级管理员"（role=2）可以从 JWT payload 里 base64 解码读出（仅用于控制 UI 显隐），安全永远以后端 hasRole("ADMIN")/40300 为准，前端只是别把按钮摆出来。

四、API 层写法与 mock 策略 ​

4.1 一个 api 模块的标准写法 ​

ts
// src/api/auth.ts
import { http } from '@/utils/request'
import type { ApiResponse } from '@/types/api'
import type { LoginDTO, RegisterDTO, TokenVO } from '@/types/auth'

export const authApi = {
  // 拦截器已把响应解包为 data，所以泛型第二参就是业务类型
  login: (dto: LoginDTO) => http.post<unknown, TokenVO>('/auth/login', dto),
  register: (dto: RegisterDTO) => http.post<unknown, TokenVO>('/auth/register', dto),
  refresh: (refreshToken: string) => http.post<unknown, TokenVO>('/auth/refresh', { refreshToken }),
}

// src/api/user.ts
export const userApi = {
  me: () => http.get<unknown, UserVO>('/users/me'),
  updateMe: (dto: UserProfileDTO) => http.put<unknown, UserVO>('/users/me', dto),
  addresses: () => http.get<unknown, AddressVO[]>('/users/me/addresses'),
  addAddress: (dto: AddressDTO) => http.post<unknown, AddressVO>('/users/me/addresses', dto),
  updateAddress: (id: number, dto: AddressDTO) => http.put<unknown, AddressVO>(`/users/me/addresses/${id}`, dto),
  deleteAddress: (id: number) => http.delete<unknown, void>(`/users/me/addresses/${id}`),
  setDefaultAddress: (id: number) => http.put<unknown, void>(`/users/me/addresses/${id}/default`),
}

types/ 里每个接口定义照抄后端 VO 字段（对照 docs/api接口库.md 的返回对象说明），后端改字段时这里同步改——这就是"文档是同步源"的落地。

4.2 mock：契约先行，按函数粒度切换 ​

api接口库.md 里每个接口都有请求/响应示例，够写 fixture 了。用环境变量开关 + 函数级判断，后端完成一个阶段就把对应函数的 mock 分支删掉：

ts
// .env.development.local：VITE_USE_MOCK=1 开启
const USE_MOCK = import.meta.env.VITE_USE_MOCK === '1'

export const productApi = {
  page: async (q: ProductQuery): Promise<PageResult<ProductListVO>> => {
    if (USE_MOCK) return productFixtures.page(q)        // src/mocks/product.ts，照 openapi.yaml schema 造数
    return http.get<unknown, PageResult<ProductListVO>>('/products', { params: q })
  },
  // ...detail / reviews 同理
}

fixture 造数的铁律：字段名、类型、金额字符串格式与 openapi.yaml 完全一致。这样后端阶段完成、删掉 mock 分支时页面零改动——fixture 就是在"预测"后端输出。

进阶替代：MSW（Mock Service Worker）在网络层拦截请求，mock 更集中；学习项目用上面的函数级开关最直观，两者不冲突，想练主流工具可以换。

每个页面的开发套路（与后端五步法对应）：

  1. 查契约：api接口库.md 找到该页面的接口，确定入参/出参/错误码；
  2. 建 api 函数 + 类型定义（mock 未删就先配 fixture）；
  3. 页面骨架：Element Plus 表单/表格/分页组件 + 加载态（v-loading）；
  4. 接数据：mounted/onMounted 调 api，catch (e) 里展示 e.message；
  5. 联调验收：对照 api接口库.md 的示例 JSON 逐字段核对。

几个关键页面的业务提醒 ​

  • 登录/注册：注册成功即已登录（后端直接发 Token），登录后跳 route.query.redirect || '/'。
  • 结算页：先 POST /orders/preview 展示金额试算 → 用户确认后 POST /orders（带 Idempotency-Key）→ 拿 orderNo 跳支付页。用户改地址/数量后必须重新 preview，金额以后端为准，前端不算钱。
  • 模拟支付：POST /orders/{orderNo}/pay 返回 PayResultVO（paymentNo、模拟支付参数）→ 支付页做"支付成功"按钮，调 POST /payments/callback 模拟渠道回调（字段对照后端 PaymentCallbackDTO，联调时和后端约定模拟验签值）→ 成功后跳订单详情。这个页面将来就是接真实支付渠道的接缝。
  • 商品列表：排序下拉（default/price_asc/price_desc/sales/newest）、价格区间、分类/品牌筛选全部走 query 参数，翻页用 PageResult.page/total 驱动 Element Plus 的 el-pagination。

六、联调规范 ​

  1. 启动顺序：docker compose up -d（MySQL/Redis）→ 后端 8080 → 前端 npm run dev（5173，已配代理）。
  2. 请求路径只写相对路径 /api/v1/...，不写 http://localhost:8080——这样 dev 走 Vite 代理、生产走 nginx 代理，前端代码零改动。
  3. 联调出问题先看 traceId：后端日志带 [traceId]，前端把 ApiError 的 traceId 展示出来（或 console.warn），两边一对照就能定位。
  4. 用 curl 校准：页面行为可疑时，先用 curl 直接打后端接口排除前端因素（curl 命令见实施计划阶段回归清单）。
  5. 每个功能两端同天联调：不要前端攒一堆 mock 页面最后统一接，记忆会失联；后端完成阶段 N 的当天，就把阶段 N-1 的 mock 分支切到真接口跑一遍。

七、容易踩的坑（写代码前先读一遍） ​

  1. HTTP 恒为 200：判断成败只看 body.code，永远不要依赖 HTTP status。
  2. 金额是字符串：展示直接用，计算先 toCents()，禁止 Number("99.90") + ...。
  3. null 字段整个缺失（non_null）：可选链 + 默认值，TS 类型里可空字段标 ?。
  4. 刷新会轮换：refresh 成功后旧 accessToken 也建议作废（直接覆盖），两个 token 同时替换；且刷新必须单飞（见 2.3），否则并发请求会互相顶掉 refresh 造成"越登越掉线"。
  5. 单设备互踢：后端白名单按 userId 单 key，另一设备登录会使本设备 refresh 失效——下次刷新 40100 自动登出属预期行为，不是 bug。
  6. Idempotency-Key 时机：在"点击下单"时生成，请求失败重试复用同一个 key，成功后清除。
  7. 40300 的两层含义：入口层（用户 Token 访问 /admin/**）由后端过滤器直接返回，方法层（改别人资源）由业务抛出——前端统一提示"无权限"，不要区分。
  8. 时间格式 yyyy-MM-dd HH:mm:ss：直接展示即可，要做相对时间（"3分钟前"）先转 new Date(s.replace(' ', 'T'))。

八、打包与部署（nginx 上场日） ​

前后端 MVP 跑通后做一次"部署日"，把网页从 dev server 里解放出来：

bash
npm run build     # 产出 dist/（注意：VITE_ 环境变量在打包时内联，改环境变量必须重新 build）

nginx 配置（并进现有 docker-compose，四容器：nginx + app + yuki-mysql + yuki-redis）：

nginx
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    # 接口透传：后端自带 /api/v1 前缀，原样转发
    location /api/v1/ {
        proxy_pass http://app:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # SPA history 路由：刷新不 404
    location / {
        try_files $uri $uri/ /index.html;
    }
}

部署日同时验证两件事：前端代码里没有写死 localhost 的 URL（都能跑通就证明没有）；真实环境下登录 → 浏览 → 加购 → 下单 → 支付全链路行为与 dev 期一致。
