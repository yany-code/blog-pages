Kafka 学习笔记 ​

我看完了项目当前的 Kafka 主链路。先给你一个整体认识：

在 CampusForge 中，Kafka 目前主要用来异步处理“申请通过后的通知”。 队长批准申请时，系统先把批准结果和一条“待发送的消息”保存到 MySQL；后台线程再把消息发送到 Kafka；另一个后台线程从 Kafka 读取消息，最终写入通知表。

整个过程是：

队长点击“批准申请”
        ↓
ApplicationController
        ↓
ApplicationService.approve()
        ↓
MySQL 事务①：
    1. 增加项目成员
    2. 申请状态改为 APPROVED
    3. 写入一条 PENDING 的 Outbox 记录
        ↓ 提交事务

后台发送线程定时扫描 Outbox
        ↓
MySQL 事务②：
    4. 查询并锁定一条 PENDING 记录
    5. 发送消息到 Kafka
    6. Kafka 确认收到后，将 Outbox 改为 SENT
        ↓

Kafka 保存消息
        ↓
后台消费者线程读取 Kafka
        ↓
MySQL 事务③：
    7. 将通知写入 notification 表
        ↓ 事务提交
    8. 向 Kafka 提交消费进度 offset
        ↓
申请人请求通知接口，查询 MySQL 中的通知

你先把这张图当作整篇的地图，后面我会带你对着代码一段段走。

还有一个重要区别：项目中有你之前见过的 @TransactionalEventListener 方案，那是 legacy 旧路径。当前 Docker 主应用配置的是 outbox + Kafka 路径，两条路径会根据配置选择其中一条。

一、先认识 Kafka：它在项目里是什么角色？ ​

你已经知道 MySQL 和 Redis：

  • MySQL：保存项目、成员、申请、通知等业务数据。
  • Redis：项目里主要用于 Session，也可以用于缓存。
  • Kafka：在不同处理步骤之间传递和暂存消息。

用这次的业务举例：

“申请已经被批准”

这件事发生后，系统想通知申请人。可以把它整理成一条消息：

{
  "eventVersion": 1,
  "eventType": "APPLICATION_APPROVED",
  "applicationId": 3135,
  "projectId": 4260,
  "recipientId": 8592,
  "attemptNo": 1,
  "content": "你加入项目的申请已通过。"
}

上面的数字和正文仅用于说明。

这条消息发给 Kafka 后，处理通知的代码可以在后台读取它，并把它变成一条站内通知。

这里有几个基本角色：

名词意思项目中对应什么
Producer生产者：发送消息的一方KafkaApprovalOutboxMessageSender
BrokerKafka 服务节点：接收、保存消息Docker 中的 kafka 容器
Topic主题：消息所属的分类campusforge.application-approved.v1
Consumer消费者：读取消息的一方ApprovalNotificationConsumer
Consumer Group消费者组：共同维护一份消费进度campusforge.notification.v1
Partition分区：主题中的消息存储单元主主题目前配置为 1 个分区
Offset消息在分区中的位置，以及消费者的读取进度比如消息 offset 是 0，处理后提交 1

先不用试图把这些名词全部背下来。跟着下面实际代码走一遍，它们就有位置了。

二、为什么要引入 Kafka？ ​

假设没有 Kafka，审批代码可以直接写成：

@Transactional
public void approve(...) {
    // 1. 修改申请状态
    // 2. 增加项目成员
    // 3. 写入通知
}

这个方案对于简单应用是完全可以的，并不是说用了 Kafka 才正规。

项目引入 Kafka 后，把工作拆成两部分：

审批请求线程：
    处理批准、成员、待发送记录

后台线程：
    发送消息
    读取消息
    保存通知

好处是：

  1. 审批和通知处理解耦。 审批代码不需要直接完成消费者的通知处理。
  2. 审批请求不需要等待通知写入完成。
  3. 消息有独立的传递通道。 以后如果有另一个需要关注“申请通过”事件的系统，可以设计独立的消费者组来读取。
  4. 消息处理失败可以有恢复空间。 不过具体能恢复到什么程度，要看项目自己实现了什么；Kafka 不会自动保证所有业务操作都成功。

需要注意：

“异步”指审批请求不等待通知落库，并不保证通知一定发生在客户端收到审批响应之后。事务提交后，后台线程和 HTTP 响应可能并发进行。

三、项目先是怎么接入 Kafka 的？ ​

1. 引入 Java 客户端依赖 ​

你可以类比：

MySQL 驱动：Java 和 MySQL 通信

这个项目使用的是 Kafka 原生 Java 客户端。 所以你在主代码里看到的是 KafkaProducer、KafkaConsumer，而不是 Spring Kafka 常见的 KafkaTemplate、@KafkaListener。

这不是说后者不能用，只是项目当前选了更直接的客户端写法，让发送、轮询和提交进度的步骤更明确。

2. Docker 运行 Kafka 服务 ​

看 compose.yaml (line 60)（compose.yaml:60）：

kafka:
  image: apache/kafka:4.4.0
  ports:
    - "127.0.0.1:19092:19092"

这部分的作用是：让 Docker 启动一个 Kafka 服务。

注意区分：

pom.xml 的 kafka-clients
    是 Java 程序中使用的客户端工具包。

Docker 的 kafka 容器
    才是接收和保存消息的 Kafka 服务。

就像加了 MySQL 驱动，仍然需要一个 MySQL 服务；加了 Kafka 客户端，也仍然需要 Kafka 服务。

项目里有两个访问地址：

Docker 容器中的 Java 访问：
    kafka:9092

Windows 本机 IDEA 运行的 Java 访问：
    localhost:19092

原因是两个程序所处的网络环境不同：

  • Docker 容器之间通过 Compose 服务名 kafka 通信。
  • Windows 上的 Java 通过映射到宿主机的 19092 端口访问。

这个地址配置在 compose.yaml (line 74)（compose.yaml:74）。

五、审批事务：先把业务和待发送记录一起保存 ​

核心在 ApplicationService.java (line 125)（ApplicationService.java:125）。

代码大体上做了：

@Transactional(isolation = Isolation.READ_COMMITTED)
public ProjectApplicationListItemResponse approve(...) {

    // 1. 确认当前用户和项目
    // 2. 确认当前用户是队长
    // 3. 确认申请轮次、项目状态、成员数量等

    // 4. 增加项目成员
    projectMemberMapper.insert(member);

    // 5. 申请改成 APPROVED
    applicationMapper.update(...);

    // 6. 交给通知投递组件
    notificationDelivery.publish(
            new ApplicationApprovedEvent(...)
    );

    // 7. 返回审批结果
}

你之前已经学过事务，所以这里最关键的点是：

@Transactional

它让这几项数据库操作放在同一次审批事务中。

这里的 publish() 会直接发送 Kafka 吗？ ​

不会。当前 Docker 的 Outbox 模式下，这一步只是将事件信息交给 Outbox 写入组件。

看 ApprovalNotificationDelivery.java (line 26)（ApprovalNotificationDelivery.java:26）：

public void publish(ApplicationApprovedEvent event) {
    if (useOutbox) {
        outboxWriter.append(event);
    } else {
        eventPublisher.publishEvent(event);
    }
}

分两条路：

useOutbox = true
    → outboxWriter.append(event)
    → 写入 MySQL Outbox 表

useOutbox = false
    → eventPublisher.publishEvent(event)
    → 走旧的 Spring 事件监听器

当前 Docker 主应用配置的是 outbox，所以走第一条。

这里也能回答你以前对监听器的疑问：

虽然对象名字叫 ApplicationApprovedEvent，但 new 一个对象本身不会触发 Spring 监听器。只有明确调用 eventPublisher.publishEvent(event)，才是发布 Spring 应用事件。当前 Outbox 路径没有走这一步。

六、Outbox 是什么？为什么要多一张表？ ​

项目中有一张表：

approval_outbox_event

建表 SQL 在 V010__create_approval_outbox_event.sql（V010__create_approval_outbox_event.sql）。

你可以把它理解成：

数据库里的“待发送消息清单”。

例如：

idapplication_idpayloadstatus
13135一段申请通过的 JSONPENDING

其中：

  • id：这条待发送记录的编号。
  • payload：需要发送的消息内容。
  • PENDING：待发送。
  • SENT：发送得到确认，并且 Outbox 状态已经成功更新。

为什么不能在审批代码里直接发送 Kafka？ ​

可以直接发，但会遇到一个问题：MySQL 事务和 Kafka 发送不是同一笔普通数据库事务。

假设你先更新数据库，再发 Kafka：

1. 数据库中的申请改成 APPROVED
2. 准备发送 Kafka
3. 此时应用崩溃

可能出现：

申请已经批准
但是通知消息没有成功发送

再假设先发 Kafka，再提交数据库：

1. Kafka 已收到“申请通过”
2. 数据库提交失败

可能出现：

消息说申请通过了
但是数据库里申请实际上没有批准成功

因此本项目采用：

同一个 MySQL 事务里：

申请批准
项目成员增加
Outbox 待发送记录插入

这三件事共同提交或共同回滚。

这样只要批准事务成功，就会有一条待发送记录留在数据库里，后台之后可以处理它。

具体代码在哪里？ ​

在 ApprovalOutboxWriter.java (line 22)（ApprovalOutboxWriter.java:22）：

@Transactional(propagation = Propagation.MANDATORY)
public void append(ApplicationApprovedEvent event) {

    ApprovalOutboxEvent row = new ApprovalOutboxEvent();

    row.setApplicationId(event.getApplicationId());
    row.setProjectId(event.getProjectId());
    row.setRecipientId(event.getRecipientId());
    row.setAttemptNo(event.getAttemptNo());

    row.setEventType("APPLICATION_APPROVED");
    row.setEventVersion(1);

    row.setPayload(
            JSON.writeValueAsString(...)
    );

    row.setStatus("PENDING");

    outboxMapper.insert(row);
}

MANDATORY 你之前接触过：

必须已经有事务。
如果外面没有事务，就报错。

在这里：

approve() 已经开启事务
    ↓
调用 append()
    ↓
append() 加入 approve() 的事务

因此：

插入成员 + 更新申请 + 插入 Outbox

共同成功或者共同回滚。

payload 又是什么？ ​

payload 就是消息的正文，这里是 JSON：

{
  "eventVersion": 1,
  "eventType": "APPLICATION_APPROVED",
  "applicationId": 3135,
  "projectId": 4260,
  "recipientId": 8592,
  "attemptNo": 1,
  "content": "你加入项目的申请已通过。"
}

代码中的：

JSON.writeValueAsString(...)

作用就是把 Java 数据转换为 JSON 字符串。

这里先把通知所需信息保存下来，也叫冻结快照：即使之后项目标题变化，待发送消息仍保留批准时构造好的内容。

七、谁来读取 Outbox？定时发送线程 ​

你可能会问：

Outbox 表里面有了 PENDING，谁会主动去查它？

答案是：ApprovalOutboxScheduledRelay.java (line 45)（ApprovalOutboxScheduledRelay.java:45）。

它实现了：

SmartLifecycle

你可以先把 SmartLifecycle 理解成 Spring 管理组件启动和停止的一套接口。

当相关配置开启、Spring 容器启动时，这个组件的 start() 会被调用，创建一个定时线程。

代码核心是：

task = scheduler.scheduleWithFixedDelay(
        this::tick,
        scheduler.getClock().instant().plus(initialDelay),
        fixedDelay
);

其中：

this::tick

是方法引用，可以先理解为：

到了时间就执行当前对象的 tick() 方法。

接着：

private void tick() {
    relay.sendOne();
}

也就是：

定时器
    ↓
tick()
    ↓
relay.sendOne()

多久执行一次？ ​

项目默认：

initial-delay: PT5S
fixed-delay: PT5S

PT5S 表示 5 秒。

具体含义：

启动后，默认先等待 5 秒开始第一轮。

每一轮执行完成后，再等待 5 秒开始下一轮。

每轮最多处理一条 Outbox。

例如：

12:00:00 启动应用
12:00:05 开始第一轮

假设第一轮耗时 1 秒
12:00:06 完成第一轮
12:00:11 开始第二轮

因此消息什么时候被发出，取决于它到达时后台线程正处在哪个阶段；不是每条消息都固定等待整整 5 秒。

同时要记住：这个发送节奏是项目当前自己的实现方式，不是 Kafka 每 5 秒才能发一条的限制。

这个线程是 Kafka 自动创建的吗？ ​

不是。

它是项目自己写的：

ApprovalOutboxScheduledRelay

由 Spring 管理生命周期，内部使用：

ThreadPoolTaskScheduler

来启动定时任务。

2. 调用 send() ​

代码中真正发送的是：

拆成两步更容易看懂：

ProducerRecord<String, String> record =
        new ProducerRecord<>(topic, key, payload);

含义分别是：

new ProducerRecord<>(topic, key, payload)

创建一条准备发给 Kafka 的消息，包含：

消息 Key

十、Kafka 收到消息后，Outbox 为什么改成 SENT？ ​

发送成功并取得确认后，ApprovalOutboxRelay.java (line 64)（ApprovalOutboxRelay.java:64） 继续执行：

    throw ...;
}

对应 SQL 大体是：

UPDATE approval_outbox_event
SET status = 'SENT'
WHERE id = ?
  AND status = 'PENDING'

作用是：

只有当前还是 PENDING，才改成 SENT。

之后发送线程的 MySQL 事务提交。

但这里请区分两个状态：

Outbox SENT：
    发送已经得到确认，并且 Outbox 状态更新成功。

通知已经生成：
    消费者已经把消息处理并写入 notification 表。

十一、什么是 Topic、Partition 和 Offset？ ​

这几个词在实际代码里会一起出现。

Topic：消息分类 ​

项目主题：

campusforge.application-approved.v1

里面放的是申请批准事件。

可以把它暂时想成一个“专门存放申请通过消息的栏目”。

Partition：主题中的分区 ​

一个 Topic 可以有一个或多个 Partition。

当前项目主主题只有一个：

Topic: campusforge.application-approved.v1

Partition 0:
    消息 0
    消息 1
    消息 2
    ...

以后分区多了，可以让不同分区分别处理消息；但一个分区内部有自己的顺序和位置编号。

Offset：分区里的位置 ​

假设 Kafka 保存了：

Partition 0：

offset 0 → 第一条消息
offset 1 → 第二条消息
offset 2 → 第三条消息

消费者处理完 offset 0 之后，会提交：

nextOffset = 1

意思是：

我已经处理完位置 0，下次应从位置 1 继续。

不是提交 0，而是提交下一条要读取的位置。

十五、为什么必须先写数据库，再提交 Offset？ ​

消费者的代码顺序是：

String dbResult = writer.save(
        record.key(),
        record.value()
);

long nextOffset = record.offset() + 1;

consumer.commitSync(...);

顺序非常关键：

① 写通知
② 数据库事务提交成功
③ 再提交 Kafka 消费进度

假设有一条消息：

offset = 0

成功处理后提交：

nextOffset = 1

告诉 Kafka：

这个消费者组下次从位置 1 继续。

如果先提交 Offset，再写数据库会怎样？ ​

假设顺序反过来：

1. 提交 nextOffset = 1
2. 准备写 notification
3. 应用突然停止

恢复后，消费者组可能从 1 开始，而 0 对应的通知其实没有写入。

结果就是：

Kafka 认为这条消息已经处理过。
实际通知没有保存。

所以项目采用先写数据库，再提交进度。

Kafka 会在消费后立即删除消息吗？ ​

不能这样理解。

消费者提交 Offset 是记录这个消费者组的处理位置；Kafka 消息还会按照主题的保留策略管理。

当前项目 Docker 配置的保留时间是：

168 小时，也就是 7 天。

这不是说通知只保留 7 天：7 天说的是 Kafka 消息的配置，已经写入 MySQL 的通知是另一回事。

十六、如果消息重复消费怎么办？ ​

即使使用了“先写通知，再提交 Offset”，仍有一个小时间窗口：

1. 通知已经写入 MySQL，并提交成功
2. 还没来得及提交 Kafka Offset
3. 应用停止

再次启动后，Kafka 可能再次把同一条消息交给消费者。

如果没有处理重复的机制，就可能出现两条一样的通知。

项目的应对方式在 ApprovalNotificationConsumerWriter.java (line 43)（ApprovalNotificationConsumerWriter.java:43）：

尝试插入 notification
    ↓
如果插入成功
    → 返回 INSERTED

如果遇到符合条件的 MySQL 重复键
    ↓
原插入事务先回滚
    ↓
另开只读事务查询已存在的通知
    ↓
核对申请、轮次、类型、项目、接收人、正文
    ↓
完全一致
    → 返回 ALREADY_EXISTS

也就是说：

重复消息不一定代表出错；如果数据库中已经有完全对应的通知，就可以认为这次通知已经处理过。

而且代码不会因为重试而覆盖原通知的已读状态。

但如果数据对不上，或者发生其他数据库错误，代码不会随便当作成功，也不会提交消费进度。

这就是业务里的幂等处理：同一个事件多次到达，尽可能只产生一份对应的通知结果。

十七、Kafka、MySQL 出故障时会怎样？ ​

结合当前代码，可以分几种情况。

情况一：审批时 Outbox 写入失败 ​

插入成员
更新申请
插入 Outbox 失败

由于它们在同一个审批事务中：

审批事务回滚
成员和申请更新也回滚

不能出现“审批成功但这一次连待发送记录都没有写下”的正常成功结果。

情况二：Outbox 已保存，但 Kafka 发送失败 ​

后台发送线程记录错误，后续定时轮次会继续扫描待办。

不过要注意：

  • Kafka 确认和数据库提交属于两个系统。
  • 网络超时等情况下，发送结果可能不确定。
  • 不能简单断言“只要报错，Kafka 一定没收到”。

例如 Kafka 已经收到消息，但更新 Outbox 状态失败，后续可能再次发送同一事件，所以消费者侧仍要做幂等处理。

情况三：消费者写通知失败 ​

当前消费者不会继续假装这条消息处理成功，也不会正常提交这条消息的 Offset。

代码会关闭当前消费者并停止该后台消费循环，避免直接跳过出错消息。

当前项目没有完整实现消费者自动恢复、退避重试和死信队列。 消费线程故障停止，并不一定代表整个应用的 HTTP 页面都无法访问。

另外，健康检查正常也不能直接证明这个后台消费者仍在正常工作。这里描述的是源码和项目现有设计边界；我这次没有做实时故障演练。

十八、把三个事务和三个执行位置连起来 ​

你以前已经学过 @Transactional，这里用这个知识把整条链串起来：

阶段谁执行事务做什么
审批HTTP 请求线程成员、申请状态、Outbox 记录共同提交
发送Outbox 定时线程锁定待发送记录、等待 Kafka 确认、更新 Outbox 状态
消费通知消费者线程写入通知表；提交数据库后再提交 Kafka Offset

可以画成：

【HTTP 请求线程】

Controller.approve()
    ↓
ApplicationService.approve()
    ↓
MySQL 事务①
    ├─ 插入成员
    ├─ 更新申请
    └─ 插入 Outbox
    ↓
提交


【Outbox 定时线程】

tick()
    ↓
ApprovalOutboxRelay.sendOne()
    ↓
MySQL 事务②
    ├─ SELECT ... FOR UPDATE
    ├─ 发送 Kafka 并等待确认
    └─ 更新 Outbox 为 SENT
    ↓
提交


【Kafka 消费线程】

consumeLoop()
    ↓
consumeOne()
    ↓
poll() 获取 Kafka 消息
    ↓
MySQL 事务③
    └─ 插入 notification
    ↓
提交 MySQL
    ↓
commitSync() 提交 Kafka Offset

其中，Kafka 发送并不属于 MySQL 事务。事务②是在持有数据库事务和行锁期间调用 Kafka，但这并不会让 MySQL 和 Kafka 变成一个可以一起回滚的数据库。
