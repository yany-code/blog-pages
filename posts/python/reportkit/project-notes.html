为什么这样分层 ​

这一节把散在代码注释和讲解里的设计理由收拢成一页。看代码时可以跳过，但想“记牢整体思想”就读这里——每条都是踩过坑之后才定下来的。

0. 一句话总览：依赖方向必须单向 ​

scripts/  ──────►  pipeline/{report, readers, filters, aggregate, writers}
                          │
                          ▼
                    models.py（纯数据）  errors.py（异常族）
  • 上层可以 import 下层，下层不许 import 上层。
  • models.py 和 errors.py 不 import 任何自己项目里的东西——它们是最底层，谁都依赖它们，它们不依赖谁。
  • 为什么死守这条：第 9 章的 partially initialized module 循环导入报错，根源就是两个模块互相 import。单向依赖从结构上让这种错误不可能发生。

判断新代码该放哪层，问一句：它是“读文件”、“算数”、“排版”，还是“编排”？

层只干这件事换了什么会改这里
readers文件 → Record换数据源（数据库、API、Excel）
filters决定“留哪些”换筛选语义（支持正则、支持区间）
aggregate算数（求和、分组、排名）换业务口径（改成中位数、加权重）
report把上面三步串起来加新的报告维度
writersReport → 文本/文件换输出格式（CSV、Excel、HTML）
timing横切关注点：计时、重试换重试策略（加抖动、熔断）
console横切关注点：日志配置换日志去向（文件、syslog、云）
scripts收参数、调库、打印换使用方式（CLI、Web、定时任务）

这个分层不是设计出来的，是"被需求逼出来的"：v1（90 行单文件版）能跑，但每次加功能都要动同一堆代码；拆完之后，加 JSON 输入源只动 readers、加落盘只动 writers。README 里的 scripts/report_v2/v3/v4 就是这个过程的三个快照。

1. 为什么要有 Record，而不是裸 dict ​

一句话：把“字段名”从运行时字符串变成可检查的属性。

裸 dict 版本（report_min.py）里，字段名是到处硬编码的字符串：

python
totals[row[field]] = totals.get(row[field], 0.0) + row["amount"]     # 键名拼错会在执行此处时抛出 KeyError

真实事故：我在 demos/p1_03_aggregate.py 拼 dict 时漏抄了 category 字段，结果聚合那步才炸：

text
KeyError: 'category'

Record 版本（models.py）把同样的错误变成立刻可见：

python
@dataclass(frozen=True)
class Record:
    order_id: str
    date: date
    region: str
    ...
    @property
    def amount(self) -> float:      # 派生值：算出来的，不存进数据源
        return round(self.quantity * self.unit_price, 2)

三个具体收益，验收都在 demos/p1_05_package.py：

收益dictRecord
写错字段名运行到那一步才 KeyError访问不存在的属性时 AttributeError；编辑器或静态检查器可提前提示
IDE 补全没有打 rec. 列出 8 个字段
途径管道时被改掉可能FrozenInstanceError 挡住（实测）
派生值得手动塞进 dict，容易和数据混在一起@property，天然不进数据源

代价与边界（别把 dataclass 当信仰）：

  • 字段一旦固定就不好改。如果数据源列名会变、或者要处理未知字段，裸 dict 反而更灵活。
  • 大数据量下应测量对象与字典的实际内存开销；是否使用 slots、字段数量与 Python 实现都会影响结果，不能一概判断哪一种更省内存。
  • frozen 只锁绑定，不锁内容：字段若是 list/dict，里面照样可变。本例字段全是不可变类型（int/str/float/date），所以真正安全。

2. 为什么校验必须在读文件之前（早失败） ​

一句话：用法错误立刻抛、越早越好；数据脏跳过并记录、别让程序停摆。这两类错误必须区别对待。

先看证据（demos/p1_08_failfast.py 可跑）：参数写错、文件也不存在时，报的是参数错——

text
参数: ['amount>=abc93']（故意写错）   文件: this_file_does_not_exist.csv（也不存在）
   -> 报的是 InvalidFilterError: amount 的值 'abc93' 不是数字
   说明参数校验先执行，程序在读文件之前就退出了

所以 scripts/report_v4.py 里顺序是刻意的：

python
filters = parse_filters(FILTER_EXPRS)      # 先校验参数
loaded = load_records(DATA_PATH)           # 再读数据

代价对比：读 10 万行 CSV 要几秒到几十秒，读到一半才发现条件写错，还可能是跑在定时任务里——凌晨三点白跑一场。校验的性价比永远是“越早越便宜”。

两类错误的判据，一句话：

情况谁的锅处理项目里的位置
数据脏（quantity='abc'）用户的文件跳过 + 记进 skipped，继续处理其它行readers._parse_record 抛 RecordValidationError，_iter_csv 捕获转成 SkippedLine
用法错（amount>=abc）用户敲的命令立刻抛，绝不继续filters._coerce 抛 InvalidFilterError，一路冒泡

还有一条相关的边界：文件不存在时故意不包装成自定义异常，让内置 FileNotFoundError 冒泡（实测输出 No such file or directory）。判据是——内置异常的语义是否已经说清问题？说清了就别加壳，否则调用方要多学一个异常名却得不到新信息。

3. 为什么 render_* 不写盘，而 write_* 才写 ​

一句话：纯函数好测，副作用要能被推迟。

python
def render_json(report, *, indent=2) -> str:        # 只返回字符串，不碰硬盘
def render_markdown(report) -> str:                 # 同上
def write_json_report(report, path, ...) -> Path:   # 落盘，返回路径
def write_markdown_report(report, path) -> Path:

实测（demos/p1_07_write.py）：render_json(report) 返回 1753 字符，硬盘上什么都没发生；write_* 才写出文件。

三个理由：

  1. 测试不产生垃圾文件。验收脚本 check_step3.py 里大半断言直接调 render_* 检查字符串，只有两项落盘（还写在 tempfile 临时目录里）。如果 render 偷偷写文件，每个测试用例都会在项目里留一堆残留。
  2. 预览和落盘可以同时做。report_v4.py 里 print(render_markdown(report)) 在屏幕上预览，write_markdown_report(...) 同时落盘，同一份内容两种去向。
  3. 需要新去向时不用改旧函数。以后要往 stdout 输出、要传给 HTTP 响应，直接用 render_* 的返回值即可。

Java 对照：toString() 不会偷偷写文件，Files.writeString() 才写——同一个道理，只是 Python 里没人靠接口强制，全靠自觉。

同一原则还有另一处体现：summarize() 只返回 Summary 数据，不负责打印。所以从 v3（打印到屏幕）到 v4（写进文件）时，aggregate.py 的计算逻辑一行都没改——腾出手把 Summary 搬进 models.py 是唯一的改动。

4. 为什么纯数据放 models.py ​

一句话：Summary 被 aggregate 和 report 同时需要，放在 aggregate 里就会让 report → aggregate 和 aggregate → report 形成环。

演进过程：

  • 步骤 C：Summary 定义在 aggregate.py（当时只有它用）。
  • 步骤 D：Report 需要引 Summary。如果 Report 也放 aggregate.py，那"报告编排"就和"算数"混在一个文件；如果放到 report.py，就变成 aggregate 和 report 互相 import ——正是第 9 章那个报错的成因。
  • 解法：把纯数据对象全部集中到 models.py，计算逻辑留在 pipeline。依赖从此单向：pipeline/* → models.py。

aggregate.py 现在这样处理，API 完全不变：

python
from ..models import Record, Summary      # 从 models 引进
__all__ = ["Summary", ...]                # 再对外转出，调用方两种 import 都行

所以 from reportkit.pipeline import Summary 和 from reportkit.models import Summary 都能用——内部结构变干净，对外接口没动。这是“重构的黄金标准”：先保证调用方无感，再谈结构优化。

models.py 里现在住着 5 个纯数据类，共同特征：只有字段和极少量派生属性，没有任何 IO、没有业务计算：

Record（一条合法记录）、SkippedLine（一条脏数据）、LoadResult（读一个文件的结果）、Summary（统计指标）、Report（一份报告的内容）。

自检标准：如果你在 models.py 里写了 open()、print()、sum()，那就是放错层了。

5. 为什么装饰器和日志不放在 pipeline 里 ​

一句话：它们是横切关注点——不属于任何一层，每层都可能用。

timing.py 和 console.py 与 pipeline/ 平级，都在 reportkit/ 根下。理由：

  • 计时/重试不是业务逻辑。readers 关心的是“怎么把 CSV 变成 Record”，不是“失败了重试几次”。把 @retry 塞进 readers.py，等于让“读文件”这个职责多背一个“容错策略”——换策略就要改业务代码。
  • 横切关注点必须能独立开关。现在 scripts/report_v5.py 里是调用方决定“给读文件加计时和重试”：
python
@timed
@retry(times=3, delay=0.1, exceptions=(OSError,))
def read_data(path: Path):
    return load_records(path)

load_records 本身一行没改。要不要计时、要不要重试、重试几次，是使用方的决定，不是库的决定。 这就是装饰器存在的意义（第 13 章讲的那个“接收函数、返回新函数”）。

  • 日志同理：console.setup_logging 只负责“怎么打印”，各模块只管 logger.warning(...) 说“发生了什么”。输出格式随时能改，业务代码零改动——把格式硬编码进 readers.py 就做不到这一点。

一个反例：如果你发现某个 @timed 是“所有人都必须带上的”，那就不是横切关注点了，而是该写进函数本身。判据：能删掉而不影响正确性的，才是横切关注点。

6. 装饰器最反直觉的坑：套在生成器上会失真 ​

一句话：装饰器只包住“函数被调用的那一刻”，而生成器函数被调用时一行都不执行。

实测（demos/p1_09_decorators.py 第 7 节）：

text
@timed 包一个耗时 0.06s 的生成器：
  记录到的耗时 = 0.0000s     ← 只测到"创建生成器"
  真正消费 list(g) 才干活，但那时的耗时没人记

@timed_iter 包同样的生成器：
  记录到的耗时 = 0.0606s（5 项）   ← 正确

原因就是第 12 章那条铁律：生成器函数体在第一次 next() 之前一行都不执行。@timed 的 wrapper 调用 func() 只是造了个生成器对象就返回了，time.perf_counter() 的前后差自然是 0。

解法是让装饰器自己也变成生成器——timed_iter 用 yield 逐个透传，这样计时窗口覆盖真正的迭代过程：

python
def wrapper(*args, **kwargs):
    start = time.perf_counter()
    for item in func(*args, **kwargs):     # 逐条透传, 保持惰性
        yield item
    logger.debug("... 耗时 %.4fs", time.perf_counter() - start)

代价（必须知道，否则会误判成 bug）：包装后仍是生成器，所以调用方只消费一部分就停下时，结束日志永远不会打。实测证据在 demos/p1_10_stream.py：scan 被调用 3 次（1 次中断 + 2 次完整），但“迭代完成”只出现 2 次。

给未来的伏笔：项目 2 的 LLM 流式输出会遇到同一个问题——async for 流式响应被中途取消时，收尾逻辑同样不会执行，那时要用 try/finally 或异步上下文管理器处理。

7. 日志的三条纪律（本项目实践） ​

一句话：stdout 是数据，stderr 是诊断；只配自己的 logger；终端看问题，文件留全量。

  1. stdout 给数据、stderr 给日志。setup_logging 的 StreamHandler(sys.stderr) 是刻意选的：python scripts/report_v5.py > report.md 重定向时，报告进文件、日志仍在屏幕——数据流和诊断流不能混在一条管道里。
  2. 只配 reportkit 前缀的 logger，不碰 root。console.py 里 logging.getLogger("reportkit") + propagate = False，效果是：你调 setup_logging 不会影响 urllib3、requests 这些第三方库的日志行为。库不该替调用方做全局决定（第 9 章的工程纪律，在日志上同样成立）。
  3. 终端 WARNING、文件 DEBUG。report_v5.py 实测的 output/_run.log：
text
22:03:08 DEBUG    reportkit.timing    read_data 完成（耗时 0.0003s）
22:03:08 DEBUG    reportkit.timing    save_reports 完成（耗时 0.0007s）

终端上你什么都看不到（级别不够），但事后排查时文件里有全量。判据：终端是给人扫一眼的（只要问题），文件是给事后追查的（要全量）。

两个易踩点：

  • logger.info() 默认看不见。root logger 的默认级别是 WARNING，不调 setup_logging 就只显示 warning 及以上——这就是为什么 report_v5.py 里第一件事就是 setup_logging(LOG_LEVEL)。
  • setup_logging 会先清空 handlers。否则每次调用都加一个 handler，同一行日志打印 N 次（验收里专门测了这条）。

8. 为什么退出码要分 0 / 1 / 2 ​

一句话：退出码是脚本的返回值，0 成功、非 0 失败，调用方（shell、CI、定时任务）靠它判断要不要继续。

实测本项目三种情况：

情况退出码谁给的实测消息
正常运行0main() 返回[摘要] sales_2024.csv: 合法 10 / 跳过 4 ...
参数/数据错误1我们自己 return 1错误: amount 的值 'abc' 不是数字
命令行用法写错2argparse 自己usage: reportkit ... error: argument --group-by: invalid choice: 'nosuch'

为什么这么分：用法错误是“命令敲错了”，参数错误是“内容有问题”，脚本里想分别处理时就能区分（比如 if [ $? -eq 2 ] 提示看 --help，其余情况记日志）。2 是 argparse 的固定约定，不是你定的——所以绝不要用 sys.exit(2) 表示自己的业务错误，否则会和用法错误混淆。

raise SystemExit(main()) 收尾：main() 返回 int 而不是直接 sys.exit()，好处是测试时可以直接 main(["data.csv"]) 调用，不用起子进程；check_step5.py 两种都用了——多数走子进程（能验退出码），少数直接调（快）。

KeyboardInterrupt 返回 130（= 128 + SIGINT 信号号）是 shell 惯例：Ctrl+C 中断时 $? 应为 130。

另一个相关纪律：ERROR 打到 stderr，报告正文打到 stdout。验收里专门查了这条（报告只走 stdout，日志只走 stderr），因为 python scripts/report.py data.csv > out.md 这种重定向必须只拿到纯数据。

9. pip install -e . 为什么能干掉 sys.path hack ​

一句话：以前每个脚本都手写三行 sys.path.insert，装一次包之后全都不需要了。

之前的写法（report_v2.py 到 report_v5.py 都有）：

python
ROOT = Path(__file__).resolve().parents[1]
SRC = ROOT / "src"
if str(SRC) not in sys.path:
    sys.path.insert(0, str(SRC))        # 把 src/ 塞进模块搜索路径

现在 report.py 里的写法是先试导入、失败才回退（这样别人没装包也能跑）：

python
try:
    import reportkit
except ModuleNotFoundError:
    sys.path.insert(0, str(Path(__file__).resolve().parents[1] / "src"))
    import reportkit

装包的命令与实测结果：

bash
$ python -m pip install -e .
Successfully built reportkit
Successfully installed reportkit-0.6.0

之后实测从任意目录都能跑（cd /tmp 再执行脚本）：

text
[摘要] sales_2024.csv: 合法 10 / 跳过 4 -> 过滤后 9 条, 合计 11,903.50
退出码=0

$ python -c "import reportkit; print(reportkit.VERSION, reportkit.__file__)"
0.6.0 D:\code for python\learning\projects\p1_data_tool\src\reportkit\__init__.py

-e 是 editable（可编辑）：让安装环境在开发期间使用源码目录；具体连接方式由构建后端决定。所以你改源码立即生效、不用重装——这正是开发期的正确姿势。去掉 -e 才是安装一份快照（要重装才生效）。

为什么需要 pyproject.toml：

toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "reportkit"
version = "0.6.0"
requires-python = ">=3.10"
dependencies = []

[tool.setuptools.packages.find]
where = ["src"]          # ← 关键：告诉打包器"包在 src/ 下"

where = ["src"] 是本例中显式声明包发现位置的配置；是否可自动发现以及需要哪些配置，取决于构建后端。Java 对照：pyproject.toml ≈ pom.xml 的极简版，pip install -e . 是当前 Python 环境的开发安装，不等同于 Maven 的本地仓库安装。

一个坑：pip install -e . 会在 src/ 下生成 reportkit.egg-info/ 目录（构建产物）。它已经进了 .gitignore——和 __pycache__、.venv 一样属于"本地产物、不该提交"。

10. 五条贯穿全文的判断准则 ​

把上面每个「为什么」压成可以随身带走的准则：

  1. 数据 vs 格式分离——Summary 只管数字，writers 才管千分位和百分号。所以同一份 Report 能同时渲染成 Markdown 和 JSON，不用改任何计算代码。
  2. 计算 vs 呈现分离——aggregate 算数、scripts 决定给谁看。同一份“华东 5291.00”既能进终端、进文件，明天也能进网页。
  3. 早失败，且区分错误类别——用法错立刻抛，数据脏跳过并留证据。别让“用户的文件有脏数据”变成一个让程序崩溃的异常，也别让“参数写错”跑完十万行才告诉你。
  4. 业务逻辑 vs 横切关注点分离——@timed/@retry/日志配置不写进 readers，由调用方按需叠加。能删掉而不影响正确性的，才是横切关注点。
  5. 用法错误与数据错误分开报——argparse 拦用法（退出码 2）、自定义异常拦参数与数据（退出码 1）。stdout 只放数据、stderr 只放诊断，这样重定向永远安全。

最后一条元准则：这些分层不是一次设计出来的，是被六次需求变更逼出来的——加 JSON 输入、加过滤、加落盘、加编排、加计时与日志、加命令行。所以不要一开始就想清楚完美结构：先让 v1 能跑，等第二次改同一处代码时再拆。README 里的 report_min → v2 → v3 → v4 → v5 → report.py 就是这条元准则的证据链。

过滤表达式语法 ​

<字段><运算符><值>              运算符: =  !=  >  >=  <  <=
<字段> in <值1>,<值2>,...       命中任意一个即可

例子：amount>=500、region=华东、category!=配件、date>=2024-01-20、region in 华东,华北、quantity>3

值按字段类型自动转换：quantity → int，unit_price/amount → float，date → date，其余按字符串。多个条件之间是 AND。 写错（字段不存在、值类型不对、缺运算符）会在开始读文件之前抛 InvalidFilterError / UnknownFieldError。
